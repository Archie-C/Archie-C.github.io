# PyTorch submission service

This is a separate asynchronous submission flow on the Neural Networks Rocket Control practical. The existing browser simulator is unchanged. Apply `setup.sql` in the intended Supabase project, deploy `functions/model-submissions` with JWT verification disabled (`supabase functions deploy model-submissions --no-verify-jwt`), and set `MODEL_SITE_ORIGIN` to the exact HTTPS origin of the website. Supabase supplies `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` to the function; never put the service-role key in the website or a repository. The default bucket cap is 20 MiB; set the project-wide Storage upload limit to at least that value, because the global limit takes precedence. Raising an exercise limit also requires updating the bucket and project limits and checking gateway/runtime constraints. The gateway buffers and forwards standard uploads: Supabase recommends resumable uploads above 6 MB, and its function request idle timeout is 150 seconds, so slow large transfers can fail and must be retried as a new attempt. See [Storage upload limits](https://supabase.com/docs/guides/storage/uploads/file-limits), [standard uploads](https://supabase.com/docs/guides/storage/uploads/standard-uploads), and [Edge Function limits](https://supabase.com/docs/guides/functions/limits). The website defaults to the existing project. To configure another endpoint, add `<meta name="model-submission-endpoint" content="https://your-host.example/functions/v1/model-submissions">` to the practical page head.

**Hosting limitation:** GitHub Pages and the Supabase endpoint are cross-site. The function issues a Secure, HttpOnly, SameSite=None, Partitioned cookie, but cross-site cookie behavior differs between browsers and privacy settings. The interface detects a rejected cookie, keeps the public leaderboard available, and refuses private submission operations. A participant record is created only when the browser submits an attempt or saves a name; public dashboard reads do not create records, and its one-year expiry is refreshed on dashboard visits. For reliable support in browsers that block third-party cookies, deploy a same-site HTTPS reverse proxy for this function under the site's own registrable domain, configure the endpoint to use it, and preserve `Origin`, cookies and Set-Cookie headers. GitHub Pages alone cannot provide that proxy. Verify cookie persistence across browser restarts on the deployed domains; a proxy or custom domain must not cache API responses. Changing origins or clearing site data creates a different participant. The cookie is a bearer credential; losing it loses access to the browser's history. No recovery is implemented.

### Optional same-origin gateway

For a custom domain served through Cloudflare, `same-origin-gateway.mjs` is a minimal Worker that proxies only `/api/model-submissions` to the deployed Edge Function. Add a Worker route for `your-site.example/api/model-submissions` while keeping the rest of the site routed to its existing host. Set Worker environment variables `SITE_ORIGIN` (for example `https://your-site.example`, no trailing slash) and `MODEL_FUNCTION_URL` (the complete HTTPS Supabase URL ending in `/functions/v1/model-submissions`); set the Edge Function's `MODEL_SITE_ORIGIN` to the same site origin. No Supabase key is needed by the gateway. Add `<meta name="model-submission-endpoint" content="/api/model-submissions">` to the practical page head. The gateway forwards cookies and the upload stream, enforces the site origin for mutations, refuses redirects, and disables caching. Deploying it requires control of the custom domain, its routing and Cloudflare account. Do not put a gateway on a shared domain or configure a route that replaces the rest of the website. Test real browser cookie persistence and the deployed proxy before use. GitHub Pages' default `github.io` host cannot be configured this way without a custom domain.

Apply the SQL as the project owner. It creates a private `model-artifacts` bucket, tables with RLS and no browser grants, and service-role-only RPCs. A restrictive `storage.objects` policy denies `anon` and `authenticated` access to this bucket even when other project policies are permissive. Storage RLS must remain enabled; review any additional custom database roles and policies before deployment. The function accepts only the configured origin and does not execute submitted Python. It creates a random 256-bit cookie, stores only its SHA-256 hash, and resolves ownership server-side. Each attempt uses unique paths and non-overwriting uploads. The gateway records a SHA-256 digest for each accepted artifact when its metadata update precedes queueing; a rare concurrent queue request can leave a digest unavailable. `model_queue` checks both storage objects and their sizes before making the job claimable. Uploading rows older than 30 minutes are marked failed on the participant's next submission. Failed and incomplete objects are retained; arrange an operator-controlled retention job if needed, never deleting artifacts belonging to queued or running jobs. The SQL limits each participant to three creations per minute and two concurrent uploads/queued/running jobs; shared limits of 120 new participant records and 120 attempts per minute provide an additional backstop, not complete protection against distributed abuse. Configure network-level request and storage quotas as appropriate for an anonymous public service.

Exercise configuration is stored in `model_exercises`. The browser defaults to `nn-rocket`; another exercise page can add `<meta name="model-submission-exercise" content="your-exercise-id">` and configure a matching database row. IDs must contain 1?64 lowercase letters, digits or hyphens. Both exercises use the same two artifact names and browser display-name identity, while histories and leaderboard selections remain scoped by exercise. The current exercise ID is `nn-rocket`, primary metric `score` (higher is better), with `landing_success_pct` as a public secondary metric, 128 KiB Python and 20 MiB weights limits, and a three-claim retry limit. Update configuration deliberately before accepting submissions. The two required artifact names are currently fixed by the API: `model.py` and `weights.safetensors`. The score is a numeric metric supplied by the future evaluator. Ties sort by submission timestamp, then submission UUID; execution time does not affect rank. Publishing is manual and requires a completed result with the configured numeric metric. Public responses include only published entries and configured metrics; participant IDs, artifact locations, private metadata and unpublished results are not exposed.

## Worker contract

The worker is external and is not included. Deploy `functions/model-worker` with JWT verification disabled (`supabase functions deploy model-worker --no-verify-jwt`) and configure its `MODEL_WORKER_TOKEN` secret as 64 hexadecimal characters generated from 32 cryptographically random bytes. Set this secret through the Supabase secrets mechanism, not in source control or the website. Supabase supplies `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` to the function. The worker needs only its independent token; it does not need the service-role key. Rotate the token in both locations if it is exposed. The gateway rejects requests containing an `Origin` header and does not grant browser CORS access. It exposes only the following operations; keep the token on the trusted local server and do not log it or claim tokens.

All operations are `POST` to `/functions/v1/model-worker?action=<action>`, with `Authorization: Bearer <MODEL_WORKER_TOKEN>` and `Content-Type: application/json`. JSON bodies are limited to 32 KiB. Non-success HTTP responses contain a bounded `error` string. Backend failures return 503; validation failures return 400; missing or invalid worker authentication returns 401. Do not expose the worker token, raw exceptions, file contents, or private evaluation data to students. Store and execute untrusted Python only in a separate, appropriately isolated evaluation environment.

1. Call `claim` with `{"exercise":"nn-rocket"}`. The response is `{"claim":null}` when no job is available, otherwise `claim` contains `submission_id`, `exercise_id`, `claim_token`, `attempt`, `lease_until`, `bucket`, `model_path`, `weights_path`, `model_sha256`, and `weights_sha256`. Digests may be null if queueing raced the optional metadata update; when present, verify the downloaded bytes against them. The claim atomically changes queued or expired running work to running. Fetch each artifact by calling `artifact` with `{"submission_id":"<uuid>","claim_token":"<token>","file":"model.py"}` or `"weights.safetensors"`. A successful response is the raw file as `application/octet-stream`; a 409 indicates that the claim is no longer current. Artifacts cannot be overwritten or downloaded by browser clients.
2. Renew an active lease before expiry with `heartbeat` and `{"submission_id":"<uuid>","claim_token":"<token>"}`. The response is `{"accepted":true}` or `{"accepted":false}`. False means the claim is no longer valid; stop work and discard its result. The default lease is 900 seconds; configure `lease_seconds` per exercise. A later claim reclaims an expired job, up to `max_attempts`; once exhausted the next claim marks it failed as infrastructure failure. Claims use row locks with `SKIP LOCKED`, and every reclaim issues a new fencing token.
3. On success call `finish` with `{"submission_id":"<uuid>","claim_token":"<token>","metrics":{"score":75.2,"landing_success_pct":80},"duration_ms":12000,"evaluator_version":"worker-v1","test_set_version":"test-v1","error_category":null,"metadata":{}}`. On failure set metrics to null and provide one of `model_loading`, `invalid_shape`, `runtime`, `timeout`, `resource_limit`, `evaluation`, or `infrastructure`. Duration is milliseconds from 0 to 86400000; metrics must be a flat object of numeric values and metric names of at most 80 characters; metrics and metadata are each limited to 16 KiB, and versions to 100 characters. The response is `{"accepted":true}` only if the claim was still current and unexpired. Never retry a stale finish with a new claim token. Client-facing failures use fixed messages; raw exception text and private metadata are not returned to the browser. On failure, the optional `metadata.public_error_code` can select a more specific fixed message. Only the following category/code pairs are accepted: `model_loading` with `missing_entrypoint`, `incompatible_weights`, or `dependency_missing`; `invalid_shape` with `input_shape`, `output_shape`, `non_finite`, or `out_of_range`; `runtime` with `controller_exception`; `timeout` with `time_limit`; `resource_limit` with `memory_limit`; `evaluation` with `evaluation_failed`; and `infrastructure` with `worker_interrupted`. For example, use `"error_category":"invalid_shape","metadata":{"public_error_code":"non_finite"}`. Unknown codes, category mismatches, and codes on successful results are rejected; omit the code to use the category message. A worker may keep additional non-public diagnostics in metadata, but should avoid secrets or test examples.

The underlying database RPCs remain restricted to the Supabase service role for the Edge Functions. Administrators can call them directly for maintenance, but the regular worker should use the narrower gateway rather than hold a service-role key.

Status transitions: `uploading → queued → running → completed|failed`; an upload may fail directly, and expired running jobs can be reclaimed until the attempt limit. Only a worker finish can mark an evaluation completed. `started_at` is reset on reclaim, so execution duration and running elapsed refer to the current/final claim. Queue wait accumulates the initial queued period and any time after a lease expires before the next claim or terminal failure; it excludes time during active claims. Queue wait for previously recorded claims that predate this field is shown as unavailable, because earlier retry intervals cannot be reconstructed. Results are polled every 10 seconds; browser API requests time out after 30 seconds and individual uploads after 140 seconds so a stalled connection does not leave the controls busy indefinitely. If queue confirmation is lost, the browser checks the actual status; an uploading attempt can be retried or cancelled from its history details. The server refuses to queue it unless both valid artifacts are present. A new completed attempt never changes the published selection.

For this submission flow, `model.py` must export `create_model()` with no arguments, returning a `torch.nn.Module`. The worker should instantiate it and load the `weights.safetensors` state dictionary strictly by name. `forward` receives a float32 tensor of shape `(batch, 12)` with the twelve raw observation values in the order shown in the practical's controller guide. It returns a finite tensor of shape `(batch, 2)`: thrust in `[0, 1]` and gimbal in `[-1, 1]`. Any feature normalization must be part of the model and its saved state. The worker must reject mismatched shapes, non-finite or out-of-range outputs. This protocol is distinct from the browser-side `Controller` and `.npz` export. The practical page links an example `model.py` and a notebook export cell that wraps the existing trained network together with its feature normalization; students need PyTorch and `safetensors` in their training environment. The operator must define and version the private evaluation flights and numeric score before deploying the worker; no evaluator, test set, or fabricated scores are supplied here.

## Checks

Run `npm run test:model-submissions --prefix a-level/tests` from the repository root. These exercise the SQL with PGlite, the gateway with mocked transport, and the gateway and SQL together with an in-process storage fixture, and the worker gateway with fenced artifact access. Run `npm run test:model-submissions-browser --prefix a-level/tests` for browser UI, same-origin identity, and browser-to-worker lifecycle tests using the actual application handlers and database with an in-process storage fixture; set `MODEL_TEST_BROWSER` to a Chromium executable if needed. The identity test closes and reopens a persistent browser profile; if the environment also loses an unrelated control cookie, it reports that restart persistence was skipped and tests explicit cookie restoration instead. PGlite serializes database calls, so its parallel-claim fixture does not verify PostgreSQL locking under real concurrent connections. These tests do not exercise a deployed Supabase Storage API. Test deployment separately with two browser profiles, both artifacts, a controlled worker claim/finish, rejected origins, blocked cookies and expired leases before opening submissions to students.
